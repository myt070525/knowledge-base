# 前端角色地图：你要做什么、其他人给你什么

> 写给**负责前端的你**。读完这篇，你应该能回答三个问题：
> ① 我在整个系统里的位置；② 我要交付什么；③ 别人会给我什么东西，我该找谁要什么。
>
> 你不需要看懂 RAG 的算法细节，但**必须懂数据怎么流**。

**联调时出问题，90% 是"字段名/格式对不上"，所以第 3 节的接口契约最重要。**

## 2. 你要交付的两个模块

### 模块一：问答界面

**功能清单**（从简到难，按这个顺序做）：

| 优先级 | 功能 | 难度 |
| --- | --- | --- |
| P0 | 输入框 + 提问按钮 + 显示答案 | ⭐ |
| P0 | 加载状态（转圈 / 打字机效果） | ⭐ |
| P0 | 显示**引用来源**（RAG 检索到哪几段知识） | ⭐⭐ |
| P1 | 多轮对话（保留上下文，能追问） | ⭐⭐⭐ |
| P1 | **流式输出**（答案一个字一个字蹦出来，像 ChatGPT） | ⭐⭐⭐⭐ |
| P1 | 历史会话列表（左栏） | ⭐⭐⭐ |
| P2 | 答案反馈（点赞/点踩）、复制、重新生成 | ⭐⭐ |
| P2 | Markdown 渲染（表格、列表、公式） | ⭐⭐⭐ |

> **"复杂前端"的第一个难点就在流式输出**。普通请求是"发一次、等一坨、收完整答案"；
> 流式（SSE：Server-Sent Events）是"连接保持不断，后端吐一块你渲染一块"。
> 这是评委最直观感受"这系统是活的"的地方。

**演示效果建议**：现场提问时，让答案逐字出现，同时右侧/下方展开"检索到的知识片段"——
这一步能同时展示 RAG 的**可解释性**，是加分项。

### 模块二：评测可视化看板 ← **这才是"复杂"的重头戏**

这个模块的**数据来源是论文的实验结果**（我已经跑出真实数据了）。
你要把论文里那两张干巴巴的表格，变成一个能交互的看板。

**要展示的四个层次**：

| 层次 | 图表 | 对应的论文内容 |
| --- | --- | --- |
| ① 总览 | 分组柱状图：6 个模型 × 5 个任务组的分数 | 论文 Table 4 |
| ② 提示策略 | 热力图 / 雷达图：5 种提示策略 × 5 个任务组 | 论文 Table 5 |
| ③ 单任务下钻 | 指标表 + 雷达图：Acc / Macro-F1 / EM / Token-F1 / LLM Score | 论文 Table 1 + 4 |
| ④ 单题明细 | 表格：题目、标准答案、模型答案、对错、分数 | predictions.jsonl |

**关键设计洞察**（这是我读完论文+跑完代码才明白的，能帮你做出加分设计）：

> **"分数不能跨题型比较"**。
> 闭集任务看 Acc（0~100），多选题看 EM/Micro-F1（0~100），
> 但开放题是 **LLM 打的 1~5 分**，量纲完全不同。
>
> 所以看板**不能**用一张图把所有任务堆在一起比大小 —— 那会误导评委和你自己。
> 正确做法：**分任务组做小图（small multiples）**，每组内部横向比模型/提示策略。

**真实数据长这样**（已经在你机器上跑出来了，可以直接拿来练手）：

```json
{
  "model_id": "qwen3_8b_llamacpp_local",
  "display_name": "Qwen3-8B (llama.cpp Vulkan, Intel Arc 140T 本地)",
  "prompt_id": "zero_shot",
  "split": "test",
  "metrics": {
    "closed_set":       { "acc": 65.4, "macro_f1": 63.4, "n": 179 },
    "multi_label":      { "em": 37.5, "micro_f1": 86.7, "n": 24 },
    "completion":       { "em": 9.4, "token_f1": 42.7, "n": 139 },
    "open_generation":  { "llm_score": 2.96, "n": 327, "scored_n": 327 },
    "reasoning":        { "llm_score": 4.15, "n": 20, "scored_n": 20 }
  }
}
```

文件位置：`runs/*/*.metrics.json`（每次实验一个），单题明细在同目录 `.jsonl`。

> 💡 **强烈建议**：拿这个真实 JSON 当你的第一个 ECharts 练习素材。
> 比看一百个图表教程都有用 —— 因为这是你自己项目的真数据，字段含义你清楚。

## 3. 接口契约草案（你和后端同学要谈的第一件事）

**现在就要做**：不要等后端写完才动。你和后端同学约定好下面这张表，
然后**用 Mock 数据（假的但格式一样的数据）先把前端写完**。
这样两边并行，谁也不等谁。

### 3.1 问答相关

| 接口 | 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- | --- |
| 提问 | POST | `/api/qa/ask` | `{ "question": "...", "sessionId": "...", "mode": "rag" }` | `{ "answer": "...", "sources": [{"title":"", "content":"", "score":0.9}] }` |
| 流式提问 | POST | `/api/qa/ask/stream` | 同上 | SSE 事件流，逐块返回 `answer` |
| 会话列表 | GET | `/api/sessions` | — | `[{ "id":"", "title":"", "createdAt":"" }]` |
| 会话历史 | GET | `/api/sessions/{id}/messages` | — | `[{ "role":"user\|assistant", "content":"", "sources":[] }]` |
| 删除会话 | DELETE | `/api/sessions/{id}` | — | `{ "ok": true }` |

### 3.2 评测看板相关

| 接口 | 方法 | 路径 | 响应 |
| --- | --- | --- | --- |
| 实验列表 | GET | `/api/eval/experiments` | `[{ "id":"", "modelId":"", "promptId":"", "createdAt":"" }]` |
| 某次实验指标 | GET | `/api/eval/experiments/{id}/metrics` | 上面那个 metrics JSON |
| 单题明细（分页） | GET | `/api/eval/experiments/{id}/predictions?page=1&size=20` | `{ "total": 689, "items": [ ... ] }` |
| 模型对比（跨实验） | GET | `/api/eval/compare?ids=a,b,c` | `[{ "experimentId":"", "metrics": {...} }]` |

### 3.3 约定死的事（避免联调时扯皮）

1. **字段名用驼峰**（`macroF1`）还是**下划线**（`macro_f1`）？—— 定死一个，全队统一；
2. **分数是 0~100 还是 0~1**？—— 论文用 0~100，建议沿用，**不要前端再乘 100**；
3. **`null` 怎么显示**？—— 比如没配 Judge Key 时 `llm_score` 是 `null`，不能显示成 0（那是在骗人），要显示 `—` 并标注"未评测"；
4. **错误格式统一**：`{ "code": 400, "message": "..." }`。

> ⚠️ 第 3 条特别重要。**把 null 显示成 0 是评审能一眼看出的硬伤**。

## 4. 你必须听懂的概念（不用会算，但要能讲）

| 术语 | 一句话解释 | 为什么你要懂 |
| --- | --- | --- |
| LLM | 大语言模型，就是"很会预测下一个词的模型" | 整个系统的大脑 |
| Prompt（提示词） | 你给模型的指令 | 论文研究了 5 种写法，看板要展示它们的差异 |
| 上下文 | 模型这次能"看到"的全部文字 | 决定了为什么要做 RAG |
| RAG | 检索增强生成：**先去知识库查资料，再让模型照着资料回答** | 系统的核心卖点，也是你界面上要展示"引用来源"的原因 |
| 嵌入 / 向量 | 把一句话变成一串数字，意思相近的数字也相近 | 算法 A 用它建库，你界面上不用管 |
| 向量检索 | 按"意思像不像"找资料，而不是按关键词 | RAG 的第一步 |
| 幻觉 | 模型一本正经地胡说八道 | RAG 就是为了压制它；答辩必被问 |
| 流式输出 | 答案边生成边传给前端 | 你的技术难点 |
| Token | 模型处理文字的最小单位，也是计费和限速单位 | 影响响应速度 |

**答辩可能被问到的"前端相关"问题，提前准备**：

- "你们前端怎么保证答案是一边生成一边显示的？" → 答 SSE / EventSource
- "评测看板为什么不做成一张总排名图？" → 答 量纲不同（Acc vs 1~5 分），强行比会误导
- "如果模型答错了，用户能看出来吗？" → 答 我们展示引用来源，用户可以核对

## 5. 前端最容易踩的坑（提前知道能省很多时间）

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| **跨域 CORS** | 浏览器报 `blocked by CORS policy` | 后端加 `@CrossOrigin`，或 Vite 配 `server.proxy`（开发期推荐后者） |
| **接口地址写死** | 换台电脑就跑不起来 | 用 `.env` 文件 + `import.meta.env.VITE_API_BASE` |
| **响应式丢数据** | 改了 `obj.xxx` 但页面不更新 | 用 `ref` / `reactive` 正确姿势，别直接赋值整个对象 |
| **ECharts 容器不显示** | 图表空白 | 容器必须有**明确高度**，且要在 DOM 渲染后 `init` |
| **ECharts 不随窗口变化** | 缩窗口图表溢出 | 监听 `resize` 调 `chart.resize()`，组件卸载时 `dispose()` |
| **流式中文乱码** | 答案切成半个汉字 | 用 `TextDecoder` 处理，注意按行解析 `data:` |
| **Git 冲突** | 五人协作合并冲突 | 小步提交、常拉取、按模块分文件，别多人改同一文件 |
